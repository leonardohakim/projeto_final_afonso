# Tabela ATAM - Northwind ETL

Esta tabela descreve os pontos de sensibilidade, trade-offs e decisões arquiteturais baseadas no método ATAM (Architecture Tradeoff Analysis Method), aplicando as táticas de Bass para garantir resiliência e performance.

| QA (Quality Attribute) | Scenario | Architectural Decisions | Sensitivity Points | Tradeoffs | Risks | Non-risks |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| **Availability** | Se o banco de dados oscilar ou cair temporariamente, a ingestão não deve abortar imediatamente, tolerando quedas curtas. | Uso de `tenacity` para retry com backoff exponencial no ETL; Circuit Breaker nas chamadas críticas. | Parâmetros de tempo do Circuit Breaker (failure_threshold, recovery_seconds); tempo limite do Retry. | Tempo máximo de espera da ingestão (Avail) vs Tempo de falha rápida (Perf). | Sem dead-letter queue; falha contínua após N retries perde a janela de ingestão em batch. | O Crash do dashboard não afeta a ingestão nem corrompe o ClickHouse. |
| **Availability / Resilience** | Falha no sistema principal de storage (MinIO) impede a leitura de dados. O sistema deve ter uma rota de fallback. | Pivoteamento dinâmico: bypass do MinIO e leitura direta dos arquivos CSV montados no volume local. | O caminho fixo dos arquivos (hardcoded); formato dos arquivos CSV não validados no bucket. | Desacoplamento via rede (Modif) vs Resiliência via leitura local (Avail). | O acoplamento ao disco local restringe a migração imediata para serviços totalmente serverless. | Arquivos brutos já estão protegidos contra alteração durante a leitura. |
| **Performance (Latência)** | Dashboard deve responder em < 2s sob carga normal para visualização de métricas (Top Cidades, Receita). | Uso do ClickHouse com engine `ReplacingMergeTree`; agregação SQL pushdown; cache no Streamlit com `@st.cache_resource`. | O tempo de TTL do cache no Streamlit; ordenação (`ORDER BY`) da MergeTree. | Cache prolongado (Perf) vs Visibilidade em tempo real estrita (Avail). | Degradação da latência se o volume de histórico crescer excessivamente sem particionamento. | O dataset de 100k linhas não exige particionamento complexo em curto prazo (cabe em RAM). |
| **Performance (Throughput)** | Ingestor processa os arquivos completos de pedidos em menos de 5 minutos sem estourar memória (8GB RAM host). | Ingestão em blocos otimizados para banco colunar (ClickHouse) via Python Pandas; uso de driver nativo (`clickhouse-connect`). | Uso de memória pelo Pandas; capacidade de I/O do banco destino. | Alto throughput de escrita batch (Perf) vs Consumo elevado de RAM transiente (Avail). | Pandas realiza limpeza inteira em memória, correndo risco de OOM (Out of Memory) se o arquivo crescer 10x repentinamente. | 100k linhas coube tranquilamente no limite da instância testada. |
| **Security** | Credenciais dos bancos e storage não devem vazar para o painel de visualização ou repousar abertas. | Variáveis mapeadas em `.env`; criação (planejada) de usuário `readonly` no ClickHouse para o Streamlit. | Compartilhamento do driver `admin` no estado atual; injeção via environment variables. | Separação de privilégios (Security) vs Simplicidade operacional local (Deployability). | Risco de vazamento por commit acidental de logs contendo URLs com credenciais (se logger não for limpo). | Rede do Compose blinda o acesso direto à porta do banco (apenas localhost mapeado explicitamente). |
| **Deployability** | Subir a stack em qualquer máquina em menos de 15 minutos, resolvendo dependências de forma automática. | Infraestrutura declarativa no `docker-compose.yml`; init scripts de banco automatizados; volumes nomeados. | Imagens fixadas com tag `latest`; tempos de healthcheck rígidos entre banco e aplicação. | Imagem latest (Deployability) vs Reprodutibilidade exata de longo prazo (Modifiability). | Quebra de compatibilidade em imagens `latest` se serviços como ClickHouse ou Postgres mudarem interfaces maiores. | Compose executa bem no ambiente Codespaces/Linux testado. |
